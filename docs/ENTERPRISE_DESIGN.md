# Parsons RFP Response Platform — Enterprise Design Document

**Version:** 0.1 (Draft)
**Owner:** Robert Leckie (Parsons)
**Date:** 2026-04-20

---

## 1. Vision

Parsons needs a secure, traceable, audit-ready platform that accelerates the
production of high-quality RFP responses while keeping a human expert in the
loop at every decision point. The platform ingests client RFPs, extracts
requirements, assembles proposal content from Parsons' approved knowledge
base, cross-checks Parsons' draft against a simulated competitor response,
surfaces conflicts and compliance gaps, scores the response against the RFP's
evaluation criteria, and routes the final package through an explicit
approval workflow — with every AI-generated artifact linked back to the
prompts, model versions, and source documents that produced it.

**Non-goals:** full automation without human approval, opaque AI outputs,
black-box scoring, or uncontrolled use of third-party models.

---

## 2. Guiding Principles

1. **Accuracy & traceability over automation.** Every model output carries
   provenance (prompt, persona, model+version, timestamp, inputs). Nothing
   goes to a customer without human approval.
2. **Compliance first.** Responses must demonstrably address every RFP
   requirement. Conflict/gap detection is a release gate, not an advisory.
3. **Reusable knowledge.** Past wins, capability statements, resumes, and
   pricing boilerplate live in a structured, searchable KB — not in
   individual authors' drives.
4. **Model-agnostic, provider-portable.** Prompts are versioned and tuned
   per target model. The platform supports OpenAI and Anthropic today and
   can add Azure/Bedrock without rewrites.
5. **Defense-in-depth security.** JWT auth, role-based access, audit trail
   on every mutation, encrypted secrets, PII redaction before any external
   model call.

## 3. Current State (2026-04-20)

### 3.1 Implemented

- **Auth (local).** SQLite `users` table, bcrypt-hashed passwords, JWT
  bearer tokens, `/api/auth/token`, `/api/auth/me`, `/api/auth/change-password`.
  Default admin: `Robert.Leckie@parsons.com` with forced password change on
  first login. Axios interceptor attaches token on every FE request. App
  gates on `!isAuthenticated → Login`, `mustChangePassword → ChangePassword`,
  else main shell.
- **Personas + Prompt Templates.** Personas have owned prompt templates;
  each template has a stored "refined" variant (`refined_content`,
  `refined_at`, `refined_by_model`) generated by Claude (Anthropic) with
  OpenAI fallback. `POST /api/prompts/{id}/refine` tunes the prompt for its
  declared target model. UI: two-column persona list + nested prompt cards.
- **Workflows (pipeline runner).** `POST /api/orchestrator/start-rfp-workflow`
  (auth-gated, JSON body) runs 6 steps: extract_requirements →
  competitive_analysis → competitor_response → parsons_sme →
  parsons_response → conflict_check, persisting each step as a
  `WorkflowData` row. `GET /workflows` lists runs grouped by terminal step;
  `POST /approve-step` records human approvals (with levels 1/2).
- **ParsonsServices page.** Company Overview is now the first tab; all
  13 RFP sections follow. Content pack for each section is handled by the
  existing per-section components.
- **KB foundations.** `Document` model + `document_ingestion` service for
  PDF/DOCX/OCR, `embeddings` service for semantic search.

### 3.2 Known Gaps / Debt

| Area | Gap |
|---|---|
| Workflow runs | No dedicated `WorkflowRun` table — runs are inferred by grouping `WorkflowData` rows. Orphan rows from failed runs leak into results. |
| KB | No requirement-to-KB-snippet retrieval augmentation in the workflow yet. |
| Competitive intel | `competitive_research` is a single model call — no external data sources, no structured competitor profile. |
| Conflict detection | `conflict_detector` runs only at end of pipeline. No section-level checks during authoring. |
| Scoring | No evaluation-criteria scoring; no win-probability model. |
| Approval workflow | Single boolean + approval level on a step row. No reviewer assignment, SLA, or notifications. |
| Audit trail | Logs are text files; no per-entity history, no replay. |
| Dashboard | No KPI surface (open RFPs, time-to-submit, win rate, hot issues). |
| Multi-tenancy / RBAC | `User.role` exists but is not enforced beyond persona delete. |
| Deploy / ops | SQLite only; no Alembic baseline; no CI; secrets via env; no containerization. |

### 4.2 Core Domain Model (target)

- `User`, `Role` — authn/authz (existing; extend with role enforcement)
- `Persona` — author voice/persona (existing)
- `PromptTemplate` — prompt + refined prompt, versioned (existing)
- `Knowledge` — structured KB unit (capability, past-performance,
  resume, boilerplate, pricing) with tags, access level, embedding
- `Document` — raw ingested files (RFP PDFs, KB sources) (existing)
- `RFP` — client opportunity (id, issuer, due date, files, status)
- `Requirement` — single extracted requirement with section, mandatory flag,
  evaluation weight (new)
- `ResponseSection` — authored section tied to one or more requirements
- `CompetitorProfile` — known/simulated competitor with capabilities,
  prior bids, strengths/weaknesses
- `SimulatedCompetitorResponse` — generated competitor draft per RFP
- `ConflictFinding` — detected conflict with severity and linked sections
- `Score` — criterion-level score with rubric and rationale
- `Approval` — reviewer, level, decision, comments, timestamp
- `AuditEvent` — immutable log of every mutation (who, what, before, after)
- `WorkflowRun` — top-level run record with status/percent/steps
- `WorkflowStep` — existing `WorkflowData`, renamed and foreign-keyed to run

### 4.3 Key Services (target)

- `KnowledgeService` — ingest, chunk, embed, retrieve top-k KB for a
  requirement or section draft
- `RequirementService` — extract + classify (functional / mandatory /
  evaluation criterion) from RFP text using a Claude-refined extractor prompt
- `CompetitorService` — maintain competitor profiles, generate a simulated
  competitor response using their known positioning + the current RFP
- `AuthoringService` — compose section drafts using retrieved KB, persona,
  and model. Each draft carries provenance metadata.
- `ConflictService` — run at section-save and at release; checks for
  contradictions, compliance gaps, and tone inconsistency
- `ScoringService` — score each section against RFP evaluation criteria
  using a rubric-based prompt; produce a composite win-probability estimate
- `ApprovalService` — enforce N-of-M approvals at configurable gates
  (section sign-off, release)
- `AuditService` — write immutable event on every state change; expose
  queryable stream for compliance

### 4.4 Security

- Secrets via environment (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`,
  `JWT_SECRET`) — never in DB or logs
- PII redaction layer runs before any outbound model call
- JWT with short TTL + refresh tokens (next phase)
- Row-level authorization scoped by RFP + role
- HTTPS only in production; CORS locked to known origins
- Rate limiting + retry budgets on external model calls

## 5. Phased Roadmap

### Phase 0 — Foundation (IN PROGRESS / MOSTLY DONE)
- [x] Local auth with forced-change default admin
- [x] Personas + per-persona prompt templates
- [x] Claude-powered prompt refinement
- [x] Workflows pipeline with approval tracking
- [x] Parsons Services UI with Company Overview tab
- [ ] Alembic baseline migration; DATABASE_URL env centralization
- [ ] CI (tests + lint) + pre-commit hooks

### Phase 1 — Knowledge Base & RFP Ingestion
- Introduce `Knowledge` model with type tags (capability, past-performance,
  resume, boilerplate, pricing)
- UI: KB browser (list / filter / upload / edit)
- Extend `document_ingestion` to chunk + embed + tag on upload
- Add `/api/kb` CRUD + semantic search endpoints
- Wire `AuthoringService` to retrieve top-k KB snippets for section drafts

### Phase 2 — RFPs & Requirements
- `RFP` + `Requirement` models
- UI: RFP workspace (upload, see extracted requirements, traceability grid)
- Claude-refined extraction prompt that produces structured JSON
  (`{id, text, section, mandatory, weight}`)
- Traceability: every `ResponseSection` declares which requirement(s) it
  addresses; UI shows coverage matrix

### Phase 3 — Competitive Intelligence
- `CompetitorProfile` model + manual/CSV seed
- Simulated competitor response generator (Opus-refined prompt using the
  RFP + competitor profile)
- UI: competitor library + compare view (Parsons vs simulated Acme)

### Phase 4 — Conflict & Scoring
- Section-level `ConflictService`: factual contradictions, compliance gaps,
  tone/voice drift
- `ScoringService` with rubric per RFP (evaluation criteria + weights);
  produce rationale text per score
- UI: conflict panel in section editor; scoring dashboard with
  section-by-section bars and overall win-probability

### Phase 5 — Approval Workflow & Audit
- Formalize `Approval` gates: section sign-off (SME), compliance review,
  executive release
- Notifications (email / in-app) on assigned approvals
- Full `AuditEvent` stream + compliance export
- Release button locked until all required approvals + no critical conflicts

### Phase 6 — Dashboard & Reporting
- Dashboard cards: open RFPs, in-review sections, overdue approvals,
  historical win rate, avg time-to-submit
- Per-RFP report (PDF export): requirement-coverage, conflict log,
  approvals trail, model usage
- Executive read-only view

### Phase 7 — Ops Hardening
- Postgres target (SQLite remains dev default); parameterized `DATABASE_URL`
- Docker compose for API + DB + Chroma
- Structured logging, metrics (Prometheus), traces
- Backup/restore playbook; secrets rotation runbook

## 6. Risks & Mitigations

| Risk | Mitigation |
|---|---|
| Model hallucination leaking into submissions | Mandatory human approval; provenance links; factual-conflict detector run pre-release |
| External API outages | Graceful degradation to mock + clear banner in UI (Workflows already does this) |
| Sensitive data sent to third-party models | PII/CUI redaction layer + allowlist of providers per project |
| Scope creep | Phased roadmap; each phase ships stand-alone value |
| Concurrency on SQLite under real load | Move to Postgres by Phase 5; meanwhile serialize writes |

---

## 7. Success Metrics

- **Time to submit a complete RFP response** (target: -40% vs baseline)
- **Requirement coverage** at release (target: 100% for mandatory)
- **Approved without rework** rate (target: ≥ 80%)
- **Win rate** on submitted responses (tracked, not a release gate)
- **Audit findings** (target: zero unapproved AI content in submissions)
